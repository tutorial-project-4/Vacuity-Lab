# UI 개발 계획

기준 문서: `Assets/Docs/UI_Plan.pdf` (2026-08-13 확인)

## 1. 목표와 범위

UI 기획서의 다음 화면을 Unity uGUI로 구현한다.

1. 타이틀/메인 메뉴
2. 옵션 및 조작키 화면
3. 게임 HUD
4. 대화 UI
5. 보스 전투 UI
6. 사망 UI

현재 프로젝트가 `UnityEngine.UI` 기반이고 `DialogueRunner`, `BossHealthGauge`도 같은 방식을 사용하므로 UI Toolkit이나 별도 UI 프레임워크는 추가하지 않는다.

## 2. 기획 요구사항

### 2.1 타이틀

- 제목: `Vacuity Lab`
- 게임 시작: 처음부터 시작
- 빠른 시작: 보스 1 해금 시점부터 시작
  - 튜토리얼 생략
  - 수감자와 조우 1 스크립트 생략
- Option: 설정창 열기
- End: 게임 종료

### 2.2 옵션

- 오디오 크기 조절
- 화면 흔들림 켜기/끄기
- 전체 화면 켜기/끄기
- 조작키 확인
- 타이틀에서는 메뉴 버튼으로 진입
- 게임 중에는 `Esc`로 진입
- 게임 중 옵션이 열리면 전투와 입력을 일시 정지
- 타이틀 화면으로 이동

### 2.3 기본 HUD

- 좌측 상단에 플레이어 하트 표시
- 하트 아래에 `회수된 기억 현재/전체` 표시
- 기획서 표기는 하트 6개, 기억 `3/3`

### 2.4 대화

- 화면 아래쪽에 반투명 패널 표시
- 캐릭터 초상화는 사용하지 않음
- 화자 이름과 대사만 표시

### 2.5 보스 전투

- 보스 이름과 HP 바 표시
- 사용 가능한 스킬과 쿨타임을 좌측 하단에 표시

### 2.6 사망

- 사망 오버레이 표시
- 다시 시작
- 타이틀 화면으로

## 3. 현재 코드 현황

| 기능 | 현재 상태 | 활용 방법 |
| --- | --- | --- |
| 플레이어 체력 | `PlayerHealth.HealthChanged`, `CurrentHearts`, `MaxHearts`, `Died` 제공 | HUD와 사망 UI가 이벤트 구독 |
| 보스 체력 | `BossHealth`와 `BossHealthGauge` 구현됨 | 기존 게이지를 UI 프리팹으로 정리하고 이름 표시 추가 |
| 대화 | `DialogueRunner`에 하단 패널, 화자명, 본문, 입력 잠금 구현됨 | 레이아웃과 아트만 기획에 맞게 조정 |
| 일반 대시 | `PlayerMovement` 내부에 쿨타임 존재 | UI용 읽기 전용 상태가 없음 |
| 벽 관통 대시 | `PlayerWallPhaseDash` 내부에 쿨타임 존재 | UI용 읽기 전용 상태가 없음 |
| 화면 흔들림 | `CinemachineScreenShake2D` 존재 | 전역 활성 설정 연결 지점 필요 |
| 기억 수집 | 확인되는 런타임 데이터 없음 | 게임 진행 데이터 담당과 계약 필요 |
| 설정 저장 | 확인되는 구현 없음 | `PlayerPrefs`로 최소 구현 가능 |
| 타이틀/씬 전환 | 타이틀 씬과 전환 코드 없음 | 신규 타이틀 씬 및 시작 지점 계약 필요 |
| 빌드 씬 | `SampleScene`만 등록됨 | 실제 타이틀/게임 씬으로 갱신 필요 |

## 4. 구현 원칙

- Canvas는 `Screen Space - Overlay`, `Canvas Scaler`는 `Scale With Screen Size`를 사용한다.
- 기준 해상도는 팀이 확정하되 우선 `1920×1080`, Match `0.5`로 작업한다.
- HUD는 프리팹 하나로 만들고 게임 씬마다 복제하지 않는다.
- UI는 게임 상태를 소유하지 않고 기존 컴포넌트의 이벤트와 읽기 전용 값만 표시한다.
- 옵션 값은 `PlayerPrefs`에 저장하고 시작 시 한 번 적용한다.
- 게임 일시정지 중에도 UI 입력이 동작하도록 옵션/사망 연출은 unscaled time을 사용한다.
- 현재 사용 중인 uGUI `Text`, `Image`, `Button`, `Slider`, `Toggle`을 재사용한다.
- 참고 이미지의 외형은 방향만 참고하고, 저작권이 불명확한 이미지는 프로젝트 에셋으로 복사하지 않는다.

```text
TitleScene
└─ TitleCanvas
   ├─ TitlePanel
   │  ├─ LogoText
   │  ├─ NewGameButton
   │  ├─ QuickStartButton
   │  ├─ OptionButton
   │  └─ ExitButton
   └─ OptionsPanel
      ├─ VolumeSlider
      ├─ ScreenShakeToggle
      ├─ FullscreenToggle
      ├─ ControlsPanel
      └─ TitleButton

GameplayScene
└─ GameplayCanvas
   ├─ PlayerHUD
   │  ├─ Hearts
   │  └─ MemoryCounter
   ├─ SkillHUD
   ├─ BossHUD
   ├─ DialoguePanel
   ├─ OptionsPanel
   └─ DeathPanel
```

패널은 한 Canvas 아래에서 활성 상태만 전환한다. 화면마다 별도 Canvas와 관리자를 만들지 않는다.

## 6. 최소 컴포넌트 설계

### 6.1 `TitleMenuUI`

- 새 게임, 빠른 시작, 옵션, 종료 버튼 처리
- 실제 시작 위치는 씬 이름을 직접 여러 곳에 쓰지 않고 Inspector에서 지정
- 에디터에서는 종료 대신 Play Mode 종료 처리

### 6.2 `OptionsUI`

- 볼륨 Slider, 화면 흔들림 Toggle, 전체 화면 Toggle 처리
- 열기 전 `Time.timeScale` 저장, 닫을 때 원래 값 복구
- 타이틀에서는 일시정지하지 않음
- 조작키 화면은 현재 입력 액션을 읽기 전용으로 표시

### 6.3 `PlayerHudUI`

- `PlayerHealth.HealthChanged` 구독
- `MaxHearts`만큼 하트 Image를 만들고 현재 체력에 따라 채움/비움 표시
- 기억 카운터는 진행 데이터 이벤트를 구독

하트는 최대 7개 수준이므로 풀링이나 가상화 없이 자식 Image를 재사용하는 단순 구현으로 충분하다.

### 6.4 `BossHudUI`

- 기존 `BossHealthGauge` 재사용
- 전투 시작 시 보스 이름과 게이지 표시
- 사망 또는 전투 종료 시 숨김
- 보스 이름은 Inspector 문자열로 시작하고 다국어가 필요할 때만 별도 데이터화

### 6.5 `SkillHudUI`

- 스킬별 아이콘, 키 표시, 쿨타임 오버레이 Image 사용
- 스킬 코드가 `CooldownRatio` 또는 `CooldownRemaining`을 읽기 전용으로 제공
- UI가 스킬 타이머를 별도로 계산하지 않음

### 6.6 `DeathUI`

- `PlayerHealth.Died` 구독 후 표시
- 다시 시작은 기존 보스 재도전 흐름과 플레이어 리스폰 흐름을 한 진입점에서 호출
- 타이틀 버튼은 `Time.timeScale`을 복구한 뒤 씬 전환

### 6.7 기존 `DialogueRunner`

- 신규 대화 시스템을 만들지 않음
- 현재 화자명/본문/typewriter/입력 잠금 로직 유지
- 패널 위치, 투명도, 폰트, 여백만 조정

## 7. 필요한 게임 코드 계약

UI 구현 전에 다음처럼 작은 읽기 전용 계약만 추가한다.

```csharp
// 예시 이름이며 담당 코드 스타일에 맞춰 조정
public float CooldownRemaining { get; }
public float CooldownRatio { get; }
public bool IsAvailable { get; }
```

기억 진행 데이터에는 다음이 필요하다.

```csharp
public int CollectedMemories { get; }
public int TotalMemories { get; }
public event Action<int, int> MemoryChanged;
```

새 게임과 빠른 시작은 동일한 게임 진입 함수를 사용하고 시작 체크포인트만 다르게 전달한다.

```text
StartGame(NewGame)
StartGame(Boss1Unlocked)
```

## 8. 작업 순서

### 1단계 — 결정 및 공통 기반

- 실제 플레이 씬과 타이틀 씬 이름 확정
- 새 게임/빠른 시작의 정확한 스폰 위치와 진행 플래그 확정
- 하트 표시 기준 확정
- 기억 총개수와 저장 주체 확정
- HUD/메뉴용 폰트와 아이콘 확보
- Build Settings에 필요한 씬 등록

완료 조건: UI가 호출할 게임 시작·진행 데이터 계약이 문서로 확정됨.

### 2단계 — 플레이 HUD

- `GameplayCanvas` 프리팹 제작
- 하트 HUD를 `PlayerHealth` 이벤트에 연결
- 기억 카운터 UI 제작
- 해상도와 화면비별 Anchor 검증

완료 조건: 체력 증감·최대 체력 변경이 즉시 반영되고 HUD가 16:9 및 넓은 화면에서 겹치지 않음.

### 3단계 — 대화 및 보스 HUD

- 기존 대화 패널을 기획 레이아웃으로 정리
- 보스 이름과 HP 바를 화면에 배치
- 전투 시작/종료에 따른 표시 상태 연결

완료 조건: 일반 플레이에서는 보스 HUD가 숨겨지고 보스전 중에만 표시됨.

### 4단계 — 스킬 HUD

- 일반 대시와 벽 관통 대시의 쿨타임 읽기 전용 API 추가
- 아이콘과 쿨타임 오버레이 연결
- 사용 불가/사용 가능 상태 시각화

완료 조건: 실제 스킬 쿨타임과 UI가 한 프레임 이상 지속적으로 어긋나지 않음.

### 5단계 — 옵션

- 공통 `OptionsPanel` 프리팹 제작
- 볼륨, 화면 흔들림, 전체 화면 연결
- 조작키 표시
- 게임 중 `Esc` 열기/닫기 및 일시정지 처리
- `PlayerPrefs` 저장/불러오기

완료 조건: 타이틀과 게임에서 같은 설정을 사용하고 재실행 후 값이 유지됨.

### 6단계 — 타이틀

- `TitleScene` 제작
- 게임 시작/빠른 시작/옵션/종료 연결
- 빠른 시작 분기 검증

완료 조건: 두 시작 방식이 각각 올바른 진행 위치로 진입함.

### 7단계 — 사망 UI와 재도전 통합

- 사망 오버레이 제작
- 다시 시작을 플레이어·보스 리셋 흐름과 연결
- 타이틀 이동 연결
- `Time.timeScale` 복구 안전망 추가

완료 조건: 사망 → 다시 시작과 사망 → 타이틀 양쪽에서 입력·시간·HUD가 정상 복구됨.

### 8단계 — 통합 QA

- 16:9, 16:10, 울트라와이드 화면비 확인
- 키보드만으로 모든 버튼 이동과 선택 가능 여부 확인
- 옵션/대화/사망 UI가 동시에 열리지 않는지 확인
- 일시정지 중 전투 타이머가 진행되지 않는지 확인
- 씬 재진입 시 이벤트 중복 구독이 없는지 확인
- 보스전 재도전 후 체력·보스 게이지·쿨타임 UI 초기화 확인

## 10. 확정이 필요한 항목

1. 기획서의 하트 6개가 고정 최대치인지, 현재 코드의 기본 4/강화 7을 따를지
2. 기억 `3/3`이 전체 게임 고정값인지 구간별 값인지
3. 빠른 시작이 개발용 버튼인지 최종 사용자 기능인지
4. 빠른 시작 시 적용할 체크포인트, 해금 스킬, 기억, 체력 상태
5. 보스 HUD를 전투 트리거 시 표시할지 보스 활성화 시 표시할지
6. 좌측 하단에 표시할 정확한 스킬 목록
7. 마스터 볼륨만 필요한지 음악/효과음 분리가 필요한지
8. 화면 흔들림 Off가 모든 흔들림을 완전히 막아야 하는지 강도 0으로 처리할지
9. 조작키가 고정 안내인지 실제 키 리바인딩까지 필요한지
10. 사망 후 다시 시작 범위가 현재 방, 체크포인트, 전체 게임 중 무엇인지

## 11. 권장 첫 작업

먼저 `UI-1`과 `UI-2`를 진행한다. `PlayerHealth` 이벤트가 이미 있어 게임 로직 변경 없이 HUD를 완성할 수 있고, 이후 화면들의 공통 Canvas와 스타일 기준도 함께 검증할 수 있다.

상태 정의:

- `구현`: 요구 동작이 코드에 연결됨. 최종 아트 또는 QA만 남을 수 있음.
- `부분 구현`: 동작 일부가 임시 처리이거나 문서 완료 조건을 충족하지 못함.
- `미구현`: 표시용 placeholder 외에 실제 게임 데이터 연결이 없음.

### 12.3 빠른 시작 상세 계약

사용하는 `PlayerPrefs`:

| 키 | 값 | 의미 |
| --- | --- | --- |
| `game.quickStartUnlocked` | 없음/`0`, `1` | 빠른 시작 잠금/해금 |
| `game.startMode` | `0`, `1` | 새 게임/빠른 시작 |

동작 순서:

1. 타이틀은 `game.quickStartUnlocked != 1`이면 빠른 시작 버튼을 비활성화하고 `빠른 시작 · 잠김`으로 표시한다.
2. `Boss.BeginBattle()` 이후 플레이어가 사망하고 `BossHealth.IsDead == false`이면 `game.quickStartUnlocked=1`을 저장한다.
3. 빠른 시작 버튼은 `game.startMode=1`을 저장하고 `boss-semi-complete-arena`를 연다.
4. `GameplayUI.Start()`는 `BossBattleStartTrigger`의 Collider 오른쪽 끝에서 1 unit 떨어진 위치로 플레이어를 Respawn한다.
5. 새 게임 버튼은 `game.startMode=0`을 저장하므로 일반 Scene 배치 위치를 유지한다.

현재 프로젝트에는 스토리 진행, 스킬 해금, 기억 저장 데이터가 없다. 빠른 시작은 보스 방까지의 이동을 생략하는 것만 보장한다. 진행 데이터가 추가되면 3단계와 4단계 사이에서 보스 방 진입 조건과 필요한 스킬/스토리 플래그를 복원해야 한다.

에디터 테스트용으로 `Title UI` 컴포넌트 Context Menu에 다음 명령이 있다.

- `Test: Lock Quick Start`: 해금 키 삭제
- `Test: Unlock Quick Start`: 해금 키 강제 저장

명령 실행 후 Play Mode를 다시 시작해야 버튼 초기 상태가 갱신된다.

### 12.4 옵션 저장 계약

타이틀과 게임 UI가 동일한 키를 사용한다.

| 키 | 타입/기본값 | 적용 대상 |
| --- | --- | --- |
| `ui.masterVolume` | `float`, `1` | `AudioListener.volume` |
| `ui.screenShake` | `int`, `1` | `CinemachineScreenShake2D.Enabled` |
| `ui.fullscreen` | `int`, 현재 화면 상태 | `Screen.fullScreen` |

화면 흔들림 Off는 새 흔들림 요청을 무시하고 이미 시작된 흔들림도 다음 카메라 갱신에서 종료한다.

### 12.5 후속 구현 순서

#### P0 — 기능 완료에 필요한 작업

1. 기억 진행 데이터 구현 및 HUD 연결
   - `CollectedMemories`, `TotalMemories`, `MemoryChanged`를 제공하는 게임 진행 주체를 정한다.
   - `GameplayUI`의 고정 문자열을 이벤트 기반 갱신으로 교체한다.
   - 완료 조건: 수집, Scene 재진입, 새 게임에서 숫자가 정확히 갱신된다.
2. 보스 HUD 가시성 통합
   - 이름과 게이지를 같은 루트 아래에 두고 전투 시작/사망 이벤트에서 함께 전환한다.
   - 완료 조건: 전투 전 숨김, 전투 중 표시, 보스 사망 후 숨김이다.
3. 재도전 진입점 구현
   - 현재 Scene 재로드를 `Boss.ResetForRetry()`와 `PlayerHealth.Respawn()` 호출로 교체한다.
   - 보스 입구 Respawn 위치를 Scene 오브젝트 또는 Inspector 참조로 확정한다.
   - 완료 조건: 플레이어·보스·기믹·게이지·쿨타임·`Time.timeScale`이 한 번에 초기화된다.
4. 게임 옵션에 타이틀 이동 추가
   - 이동 전 `Time.timeScale=1`을 보장한다.
   - 완료 조건: 옵션에서 타이틀로 이동한 뒤 타이틀 입력과 애니메이션이 정상 동작한다.
5. 패널 충돌 방지
   - 대화 중 옵션 진입 정책을 확정하고 옵션/대화/사망 UI가 동시에 입력을 받지 않게 한다.
   - 완료 조건: 화면별로 최상위 패널 하나만 입력을 차지한다.

#### P1 — 기획 완성도 작업

1. 하트, 대시, 벽 관통 대시의 최종 아이콘을 확보하고 임시 사각형을 교체한다.
2. 스킬 해금 및 실제 사용 가능 상태를 읽기 전용 값으로 노출해 HUD에 반영한다.
3. 하트 최대치를 기획의 6개 또는 현재 게임 코드의 4/7 중 하나로 확정한다.
4. 조작키 안내를 Input Action에서 읽을지 고정 문구로 유지할지 확정한다.
5. 게임 Scene과 보스 이름을 코드 상수 대신 Inspector 값으로 옮긴다. Scene/보스가 둘 이상 생길 때 진행한다.
6. 여러 게임 Scene에서 같은 HUD가 필요해질 때만 런타임 생성 코드를 프리팹으로 전환한다.

#### P2 — 통합 QA

1. 1920×1080, 1920×1200, 2560×1080에서 겹침과 잘림을 확인한다.
2. 마우스 없이 방향키/Tab, Enter, Esc로 모든 메뉴를 이동한다.
3. 옵션 저장 후 Play Mode 또는 빌드를 재실행해 값 유지 여부를 확인한다.
4. 보스전 진입 전 사망 시 빠른 시작이 해금되지 않는지 확인한다.
5. 보스전 중 플레이어 선사망 시 해금되고, 보스 선사망 또는 동시 사망 시 해금되지 않는지 확인한다.
6. 사망 → 재시작과 사망 → 타이틀을 각각 3회 반복해 시간 정지와 이벤트 중복을 확인한다.
7. 대화 중 Esc, 대화 종료 직후 사망 등 패널 경계 상황을 확인한다.

### 12.6 인수인계 시작 절차

1. Unity `6000.4.5f1`로 프로젝트를 연다.
2. Console의 `error`를 먼저 해결한다. `CS0618`은 현재 Unity 6 사용 중단 경고이며 UI 실행을 막지 않는다.
3. `Assets/Scenes/TitleScene.unity`를 열고 Play하여 타이틀에서 시작한다.
4. 게임 HUD를 수정할 때는 `Assets/Scenes/boss-semi-complete-arena.unity`에 `Gameplay UI` 오브젝트가 한 개만 있는지 확인한다.
5. 기준 Scene에 UI 부착 또는 대화 스타일을 다시 적용해야 할 때만 `Tools/UI/Setup Gameplay UI`를 실행한다. 이 메뉴는 기존 `Gameplay UI`를 삭제하고 다시 생성한다.
6. 코드 변경 후 `dotnet build Assembly-CSharp-Editor.csproj --no-restore` 또는 Unity Console로 컴파일 오류 0개를 확인한다.
7. P0부터 완료하고 각 완료 조건을 확인한 뒤 이 상태표를 갱신한다.

### 12.7 현재 제한 및 주의점

- `GameplayUI`와 `TitleMenuUI`는 실행할 때 자식 UI를 생성한다. Play Mode 중 생성된 Hierarchy 수정은 저장되지 않는다.
- `GameplayUI.Restart()`는 현재 Scene의 Build Index를 다시 로드한다. 기준 Scene이 Build Settings에서 빠지면 재시작이 실패한다.
- 타이틀과 게임 Scene 이름이 코드에 고정되어 있다. 파일 이름을 바꾸면 `TitleMenuUI.GameScene`과 `GameplayUI.GoToTitle()`도 수정해야 한다.
- 기억 숫자 `0/3`, 보스 이름 `WARDEN-01`, 조작키 문구는 현재 placeholder다.
- 기존 사용자 PC의 `PlayerPrefs`에 빠른 시작 해금 키가 남아 있으면 최초 실행부터 버튼이 활성화될 수 있다. 초기 잠금 검증 전 `Test: Lock Quick Start`를 실행한다.
- 다른 작업자의 `Assets/Scenes/arena_boss_test.unity` 변경은 UI 기준 Scene과 별개이므로 UI 작업에서 덮어쓰지 않는다.

## 13. 개발 가능 여부 및 팀 결정 입력 양식

이 절은 후속 UI 개발을 팀과 함께 진행하기 위한 작업판이다. 팀에서 각 항목의 `확정된 결정` 또는 `확정된 자료`를 직접 작성한 뒤 개발 담당자에게 전달한다. 미작성 항목은 `[미정]`으로 유지한다.

작성 원칙:

- 선택지 중 하나를 남기거나 자유 형식으로 확정 내용을 작성한다.
- Scene, Prefab, 이미지처럼 실제 에셋이 있는 경우 프로젝트 상대 경로를 적는다.
- 수치와 문구는 `대략`, `추후` 대신 실제 적용할 값을 적는다.
- 결정 날짜와 결정자를 함께 적으면 이후 변경 이유를 추적하기 쉽다.
- 확정 후 이 문서를 기준으로 구현하고, 구현 완료 시 12.2 상태표도 함께 갱신한다.
